# Evaluation harness

Measures how well ApplyPilot's matching systems agree with human judgement
on CV–job fit. Every model change in the ML plan is judged against this.

## Layout

| Path | What lives there |
|---|---|
| `data/cvs/` | Synthetic CV personas, one Markdown file each. YAML front matter is metadata for us; the runner strips it before any system sees the CV. |
| `data/jobs/` | `snapshot.jsonl` holds the frozen listing text and is **gitignored**. `index.csv` (job ID, provider, URL) and `pools.json` (each CV's own and neighbour candidates) are committed. Frozen so every run scores the same text. |
| `data/pairs.csv` | The 450-pair **production set**: every CV–job pair to label, with its selection bucket, language tag and listing quality. Committed. |
| `data/pairs-fulltext.csv` | The 100-pair **full-text subset** (see below), same columns plus `non_job_suspect`. Committed. |
| `data/labels/` | Labels (`labels.csv`), the calibration labels, and the one-week-later re-labels. The reference label (`label`) equals the LLM label (`draft_label`); no human review (E009). Committed. |
| `work/` | Rendered labelling sheets and raw draft files that contain or quote listing text. **Gitignored.** |
| `.env.local` | `GEMINI_API_KEY_EVAL`, the evaluation project's Gemini key. **Gitignored**; template in `.env.example`. |
| `data/gemini-sample.csv` | The fixed 100-pair sample Gemini is evaluated on (E011). |
| `cache/` | Cached model responses keyed by a hash of model + input. Makes Gemini runs reproducible and free to re-run. |
| `scripts/` | `collect-jobs.ts` builds the snapshot, `build-pairs.ts` picks the pairs (fixed seed), `render-sheet.ts` writes blind labelling sheets, `run-heuristic.ts` / `run-gemini.ts` produce predictions, `draw-sample.py` draws the Gemini sample, `gemini-daily.sh` schedules Gemini runs, `metrics.py` computes the report. |
| `results/` | One dated JSON file and Markdown table per run. Never edited by hand. |
| `LABELLING_GUIDE.md` | The 0–3 scale and rules. Read before every labelling session. |

## What the labels measure

Labels judge **the person against the role**: skills, experience and
seniority. They deliberately **ignore logistics**: location, remote or
on-site policy, relocation, time zones, salary, work authorization and
visa sponsorship. The app handles those with search filters, before
matching happens.

Consequences for the results:
- The heuristic is run with neutral logistics filters (any location, any
  employment type), so its location and authorization rules are **not
  evaluated** here. Its seniority and skill logic are.
- Hard professional requirements (a licence, a degree, a required spoken
  language) are not logistics and still count. See the labelling guide.

## Full-text subset

Adzuna snippets are cut at 500 characters, so the production set is almost
entirely thin. A separate **full-text subset** uses complete listings from
Jobicy and Arbeitnow:

- 10 CVs × (5 own-role + 3 neighbour-role + 2 random) = 100 pairs.
- Own-role candidates must contain **every** role word of the CV's
  `search_query` in the title (stricter than the production pools).
- Built by `scripts/collect-fulltext.ts` (listing pool) and
  `scripts/build-fulltext-pairs.ts` (pairs, seed 20261121).
- Disjoint from the production set and always reported separately.
- `non_job_suspect` is a **screening column only**: it marks listings that
  look like programmes, courses, gig work or something the candidate pays
  for. It never removes a listing; the final `non_job` decision is made in
  label review.

## Results

The metrics below measure **agreement with an LLM reference judge**, not
with human recruiters. The reference label for every pair was generated by
Claude Opus 5.5 following `LABELLING_GUIDE.md` and was not reviewed by a
person. Two limitations apply to every number in this table:

- **Same model, both sides.** The same model (Claude Opus 5.5) wrote the 30
  synthetic CVs and generated the reference labels, so the labels may share
  the CV author's assumptions.
- **No human agreement measured.** Agreement between these labels and human
  judgements was never measured, so a high score here does not show that a
  system agrees with recruiters.

LLM-generated labels (Claude Opus 5.5), no human review

| System | Pairs | Pairs scored | Precision | Recall | F1 | Spearman ρ | NDCG@5 |
|---|---|---|---|---|---|---|---|
| Heuristic | Production, all genuine | 429 / 429 | 0.68 [0.57, 0.78] | 0.87 [0.81, 0.93] | 0.76 [0.69, 0.83] | 0.65 [0.54, 0.75] | 0.80 [0.70, 0.88] |
| Heuristic | Full-text, all genuine | 99 / 99 | 0.60 [0.38, 0.83] | 0.81 [0.68, 0.92] | 0.69 [0.49, 0.84] | 0.65 [0.51, 0.75] | 0.72 [0.63, 0.82] |
| Heuristic | 100-pair sample | pending | | | | | |
| Gemini | 100-pair sample | 7 / 100 so far | | | | | |

Match means label ≥ 2 against score ≥ 50; brackets are 95% CV-level
bootstrap intervals. 22 of the 550 pairs are flagged non_job and excluded
(21 production, 1 full-text), leaving 528 genuine pairs. Full tables,
including thin/full, language and own/neighbour/random subgroups, are in
`results/<date>-baselines.md` (experiment log E010, E011).

**Gemini is evaluated on a sample, not on all pairs.** The Gemini free
tier allows about 20 requests a day and no paid tier is used, so Gemini
scores a fixed 100-pair sample (`data/gemini-sample.csv`), and the
comparison is heuristic vs Gemini on exactly those 100 pairs. The heuristic
is also reported on all 528 genuine pairs. The sample rows above are
filled in when the sample is complete (E011).

How the sample was drawn (`scripts/draw-sample.py`): from the 528 genuine
pairs, stratified by set and bucket (production/full-text ×
own/neighbour/random) in proportion to stratum size, simple random
sampling within each stratum, seed 20261121. The draw never reads Gemini
predictions or the cache; cached responses are reused only for pairs that
happened to fall in the sample (5 of 100).

Sampling limitations:
- **Wider intervals.** 100 pairs give much wider intervals than 528, and
  small buckets are thin (random: 15 pairs, few or no label ≥ 2 pairs),
  so per-bucket differences are indicative only.
- **NDCG is weak.** The sample has about three pairs per CV, and a CV
  with one pair always scores NDCG 1.00; compare systems on F1 and
  Spearman.
- **Not the full-set numbers.** The heuristic's sample numbers will
  differ from its all-pairs numbers by sampling noise alone; only the
  sample rows compare the two systems.
- **Pooled sets.** The sample pools production (81 pairs, mostly thin
  listings) and full-text (19 pairs); per-set results inside the sample
  are small.
- **Collection over several days.** Gemini responses are collected over
  several days with the same model name; a silent model update by Google
  during that period would not be visible.

**Thin listings.** In production 418 of 429 genuine pairs are thin, so the
production heuristic numbers are essentially the thin-listing numbers
(F1 0.77, Spearman 0.66); the 11 full production listings contain no
label ≥ 2 pairs. The full-text set (all full listings) gives the heuristic
F1 0.69 and Spearman 0.65.

## Labelling method

Since 2026-11-21 the dataset uses **LLM-generated labels (Claude Opus 5.5), no human review** (experiment log E009). This
supersedes the earlier plan of LLM-drafted labels reviewed by a human.

- An LLM (Claude Opus 5.5, `claude-opus-5-5`) generated a label (0 to 3),
  a confidence, a listing flag and a one-line rationale for every pair,
  following `LABELLING_GUIDE.md`. It saw only the CV text and the listing
  text, never a system score, the selection bucket or persona metadata.
  It is not one of the systems under evaluation.
- The reference label is `label`, which equals `draft_label` for all 550
  pairs. `reviewed_change` and `labelled_at` stay blank: no pair was
  reviewed.
- The 10 calibration pairs (`calibration-labels.csv`) are the only
  human-labelled pairs. They shaped the guide and are not part of the
  evaluation.
- The review tool (`npm run review`) stays in the repository for a
  possible future human audit. It is not part of the current workflow.
  If an audit is run, `reviewed_change` records whether the human changed
  the label and the change rate (`yes` ÷ reviewed) is reported.

## Reporting subgroups

Every result reports these counts first, then the metrics:

| Subgroup | Definition | In job-fit metrics? |
|---|---|---|
| Non-job | `flag=non_job` in the labels | **No**, counted only |
| Genuine, thin | not non-job, `listing_quality=thin` | Yes, also reported separately |
| Genuine, full | not non-job, `listing_quality=full` | Yes, also reported separately |
| Same / cross language | `language_pair` in the pairs file | Yes, also reported separately |
| Production vs full-text | `pairs.csv` vs `pairs-fulltext.csv` | Yes, always reported as separate sets |

`listing_quality` is computed when pairs are built, before any label is
drafted or reviewed: `thin` means the provider truncated the text or it
is under 1,000 characters.

## Language subgroups

Every pair is tagged `same` or `cross` language, comparing the CV's
language with the listing's detected language. Most Turkish CVs meet
English listings, so `cross` pairs are reported as a separate subgroup:
it shows whether a system really matches meaning across languages or only
matches shared words.

## Calibration set

Ten pairs are labelled first and compared against the guide; the guide is
adjusted if needed. They come from `data/labels/calibration-pairs.csv`,
are disjoint from `pairs.csv`, and never enter the final metrics.

Round 1 (2026-11-20) changed the guide in three places: past work in the
listing's field, required core frameworks, and listing quality. All 10
calibration listings were truncated; 2 of the 10 (cal-05, cal-06) were not
real job postings. Details in `docs/experiment-log.md`, E003.

## Data policy

- **No real people.** CVs are synthetic personas. Names, emails and employers
  are fictional; universities and technologies are real so the text reads
  naturally. Never add a real user's CV, even anonymized by hand.
- **Free-tier Gemini** may use inputs to improve Google's products. That is
  acceptable only because everything sent is synthetic or already-public
  listing text.
- **Listing text is never committed.** Adzuna and Remotive terms have not
  been confirmed to allow redistribution, so `data/jobs/snapshot.jsonl`
  and `work/` are gitignored. Only job IDs, URLs and labels are committed.
  `scripts/collect-jobs.ts` documents how the snapshot was built; a
  re-collection will return different listings, so published results are
  reproducible from the cached snapshot, not from the providers.

## Splits

Train / dev / test are split **by CV**, never by pair, so the same person
never appears on both sides. The split is fixed once in `data/splits.json`
and never changed after the first result is recorded.

## Known data limits

- Adzuna cuts descriptions at 500 characters, and most snippets don't
  state requirements. The app scores the same snippets, so results
  reflect production, but labels on thin pairs are less certain. Thin
  pairs are marked in `pairs.csv` and reported as a subgroup.
- Some listings are not real jobs (training programmes, self-employment
  pitches). They are flagged `non_job` and excluded from job-fit metrics.
- Remotive's public API returns only 15 listings, so nearly all listings
  come from Adzuna.

## Workflow

1. Freeze the job snapshot: `npx tsx eval/scripts/collect-jobs.ts`.
2. Build pairs: `npx tsx eval/scripts/build-pairs.ts`.
3. Render a sheet: `npx tsx eval/scripts/render-sheet.ts main 1 60`.
4. Generate labels with the LLM following `LABELLING_GUIDE.md`; the
   reference label is the LLM label (no human review).
5. Put the evaluation Gemini key in `eval/.env.local` (copy
   `eval/.env.example`) as `GEMINI_API_KEY_EVAL`. It belongs to a separate
   Google project; eval scripts never use the app's `GEMINI_API_KEY`.
   Run the systems: `npx tsx eval/scripts/run-heuristic.ts` (all pairs) and
   `npx tsx eval/scripts/run-gemini.ts` (the 100-pair sample from
   `python3 eval/scripts/draw-sample.py`). Gemini runs daily within the
   free-tier quota via `eval/scripts/gemini-daily.sh` (launchd; see E011).
6. Run `python3 eval/scripts/metrics.py`; it writes
   `results/<date>-baselines.json` and `.md`.
7. Record what happened in `docs/experiment-log.md`, including failures.
