# Experiment log

A dated record of every experiment, including the ones that failed. Write
the entry **before** looking at results (hypothesis and setup), then fill
in the result. Never delete or rewrite an old entry; add a correction below
it instead. This log is the source for the README's "what I tried / what
didn't work" section.

## Entry template

```
## E### — <short title> (YYYY-MM-DD)
**Question:** what we want to know.
**Hypothesis:** what we expect and why, written before running.
**Setup:** data version, split, model + version, parameters, command.
**Result:** numbers with confidence intervals; link to results/<file>.
**Conclusion:** what we now believe. Surprises.
**Next:** what this changes.
```

## E000 — Project decisions (2026-11-20)

**Question:** how should the evaluation be designed so its results are trustworthy?

**Decisions:**
- Ground truth is human labels on a 0–3 scale; a pair counts as a match at
  2 or higher. Gemini is one of the systems under test, so it cannot also
  be the judge.
- Dataset target: ~30 synthetic CV personas × ~15 real listings ≈ 450 pairs,
  with deliberate hard negatives (similar-looking but wrong roles).
- CVs are written from a persona spec rather than generated by Gemini, so
  the text is not stylistically "familiar" to the model being evaluated.
- Splits are by CV to avoid leakage.
- Label reliability: one labeller; 50 pairs re-labelled by the same person
  one week later, reported as intra-rater weighted Cohen's kappa. This
  measures consistency, not agreement between different people; that
  limitation is reported.
- Location, remote policy, salary and work authorization are excluded from
  labels (see labelling guide). The heuristic is run with neutral
  logistics filters so it is not penalized for signals humans ignored.

**Next:** labelling guide, persona spec, job snapshot.

## E001 — Dataset design additions (2026-11-20)

**Decisions:**
- **Synthetic CV style is a limitation.** All 30 CVs are written by one
  model (Claude), so their style is likely more uniform than real CVs:
  cleaner structure, fewer typos, consistent tone. Mitigation: formats are
  varied on purpose (bullets, prose, mixed; short and long; with and
  without a skills section). Residual risk: systems that rely on surface
  wording may score better here than on real CVs. Reported in the README.
- **Language subgroup.** Each pair is tagged `same` or `cross` language.
  Metrics are reported overall and for the cross-language subgroup, which
  mostly means Turkish CVs against English listings.
- **Listing text stays out of git.** Only IDs, URLs and labels are
  committed, because provider redistribution terms are unconfirmed.
- **Calibration set.** Ten pairs labelled first to test the guide. They are
  excluded from the final dataset.

## E002 — CV set and job snapshot v1 (2026-11-20)

**Question:** can the providers supply a usable pool of listings for 30 personas?

**Setup:** `eval/scripts/collect-jobs.ts`; one Remotive feed request,
two Adzuna searches per CV (own role and neighbouring role) in the CV's
`search_country`; pairs from `eval/scripts/build-pairs.ts`, seed 20261120.

**Result:**
- **Remotive returns only 15 listings**, whatever the parameters.
  Category and unfiltered requests give the same 15. This also caps the
  app's own remote search, which is a product finding, not just an eval one.
- **Long queries fail on Adzuna.** The first run used role queries with
  seniority and tools ("junior data analyst sql power bi"); 8 of 60
  returned nothing, because Adzuna requires every word. Shortened to the
  core role ("data analyst") for 14 queries; every query then returned at
  least 8 results. Seniority now varies within each pool, which tests the
  seniority logic instead of filtering it out.
- **Adzuna descriptions are cut at 500 characters** (1,052 of 1,067
  listings). Only about 1 in 5 snippets (215 of 1,052) mentions
  requirements at all; many are company blurbs. The app's search scores
  exactly these snippets, so they are production-realistic, but they may
  be too thin to label reliably.
- **A third of listings are not in English** (German 124, Dutch 100,
  Spanish 37, French 30, Polish 28), so cross-language pairs come from
  English CVs too, not only Turkish ones.
- Dataset: 1,067 listings; 450 main pairs (240 own, 150 neighbour,
  60 random; 229 same-language, 213 cross, 8 unknown) plus 10 calibration
  pairs, disjoint.
- **CVs are short.** Median about 200 words, range 83 to 394. Real CVs
  are often longer. Added to the synthetic-style limitation in E001.

**Conclusion:** the pool is big enough, but snippet length is the main
threat to label quality. Calibration must answer whether snippets can be
labelled consistently.

**Next:** label the calibration set, then decide how to handle thin
listings before the main labelling.

## E003 — Calibration round 1 and labelling method (2026-11-20)

**Question:** can the guide be applied consistently, and what has to
change before the main labelling?

**Labelling method, going forward:** the dataset uses
**LLM-drafted, human-reviewed labels**. An LLM drafts a label, a rationale and a listing
flag for every pair from the guide, the CV text and the listing text; the
reviewer then reviews every pair and either accepts the draft or assigns a
different final label. The drafting model must not be one of the systems
under evaluation; each drafting run records its model identifier and
prompt version here.

**Label schema:** `draft_label` (the original draft, never edited) and
`label` (the final, reviewed label) are stored separately, plus
`reviewed_change`: blank while review is pending, `yes` if the final label
differs from the draft, `no` if the draft was accepted. Change rate =
`yes` ÷ (`yes` + `no`). Editing only the rationale (`notes`) or the flag
is not a label change. A pair counts as reviewed only after the reviewer
fills in `reviewed_change`. Existing columns were kept (`label`,
`confidence`, `flag`, `notes`, `labelled_at`); `flag=invalid` became
`flag=non_job`, and thinness moved out of `flag` into `pairs.csv`.

**Results (reported by the reviewer, original outcome preserved):**
- **cal-03** (cv-03, career changer, against *Digital Marketing
  Specialist*). Under the original guide the pair scored **2**, while the
  persona design intended a lower score ("marketing listings are traps").
  The guide had no rule on past work in the listing's field.
- **cal-04** (cv-08, senior Angular, against *Senior Frontend Developer
  (React)*). The guide gave no explicit 1-vs-2 rule when a required core
  framework is missing; "React is not Angular" was stated only for the
  reverse case.
- **Listing quality.** All 10 calibration listings were truncated by the
  provider (each exactly 500 characters, ending in "…"). Separately, 2 of
  the 10 were not real job postings: **cal-05**, a self-employment
  "personal development and leadership education" pitch, and **cal-06**, a
  paid data-analyst career programme run by a recruiter. They are marked
  `flag=non_job` in `calibration-labels.csv`.
- The per-pair calibration labels were not saved to the repository:
  `calibration-labels.csv` has the new columns but blank draft and final
  labels. Only the outcomes above are recorded.

**Guide changes:**
- **Past work in the listing's field.** Experience performing the
  advertised duties counts, if at least 1 year long and ended within the
  last 3 years; older duty experience supports at most a 1; same industry
  in a different role is domain familiarity only.
- **Required core frameworks.** Explicit 1-vs-2 table: a 2 needs paid
  work with the named framework, or with an alternative the listing
  explicitly accepts; same role and seniority in a different framework of
  the same kind is a 1; side projects and "familiar with" never count.
  Preferred frameworks never cap the score.
- **Listing quality.** `thin` is computed when pairs are built, before any
  drafting or review (truncated, or under 1,000 characters). `non_job` is
  judged during labelling and excluded from job-fit metrics.
- The worked example "Flask/FastAPI against a Django listing" changed from
  2 to 1, because the new framework rule now covers it.

**Conclusion:**
- **cal-03 under the revised rule is still 2.** The deciding evidence is 5
  years as a Digital Marketing Specialist (paid campaigns, landing-page
  tests, conversion tracking), ending March 2025, and a listing that
  explicitly accepts a digital-marketing background. That is duty
  experience, not same-industry experience. The persona's "marketing
  listings are traps" premise holds only for marketing listings whose
  duties she never performed; cv-03's twist was reworded accordingly. A
  lower score would need a rule that discounts past duties because the
  candidate has since changed field, which the guide's principle (judge
  fit, not direction) currently rejects. Open for the reviewer to confirm.
- **cal-04 under the revised rule is 1.**
- **Risk: anchoring.** Reviewing a draft can pull the reviewer toward it.
  Mitigations: read the pair before the draft, report the change rate, and
  re-label 50 pairs a week later without drafts or first labels.

**Next:** decide on replacing thin listings (proposal pending approval),
then draft and review the main labels.

## E004 — Calibration decisions (2026-11-20)

Corrections and decisions after E003, from the reviewer.

- **Calibration labels recorded** in `calibration-labels.csv`: draft
  and final labels for all 10 pairs. The reviewer accepted every draft, so
  the change rate is **0 / 10**. All 10 listings are thin (truncated). Note

- **cal-05 and cal-06 confirmed** as the two non-job postings.

  from a different ecosystem (Angular for React). The guide lists the
  ecosystems explicitly, because "same language" alone would put Angular
  and React together (both TypeScript). The Flask-against-Django worked
  example is back to **2**. **cal-04 stays 1.**
- **Thin-listing replacement approved**, starting with a pilot on the
  first 50 listings in replacement order. The pilot reports its hit rate
  and problems; the pool is not changed until the reviewer approves.

## E005 — Thin-listing replacement pilot (2026-11-20)

**Question:** can the approved plan replace thin Adzuna listings with
comparable full-text postings from Greenhouse, Lever and Ashby?

**Setup:** `eval/scripts/replace-thin.ts --limit 50`, seed 20261120. The
target order written to `data/jobs/replacement-plan.csv` has 275 listings
(289 affected pairs) with 90 retained thin pairs; the proposal's 274/290
came from an earlier Python dry run with a different random generator.
The pilot covered targets 1 to 50, all own-role listings whose snippet
states no requirement. 74 company slugs × 3 platforms = 222 list requests,
plus 14 imports through the app's adapter, throttled to one per second.
Nothing in `pairs.csv` or the snapshot was changed.

**Result:**
- Raw outcome: 2 same-posting, 12 comparable, 36 none (28% hit rate).
- **Boards found for only 2 of the 50 companies** (Stripe, Nebius, both
  on Greenhouse). Most target companies are recruiters and staffing
  agencies (Robert Half, SThree, emagine, Free-Work and others) or large
  employers whose careers sites run on other systems.
- **Step B (comparable) is not fit for purpose as written.** The pool's
  role-word rule needs only half the query words, so a single shared word
  passes: a *Data Analyst* target got *Backend Engineer, Data* and
  *Product Marketing, Data Products*. On manual review only 3 of the 12
  are genuinely comparable (#24 full-stack, #38 data-centre technician,
  #42 data science).
- **Same posting:** #14 is the same Stripe internship. #31 has the same
  title at the same company, but in Germany instead of the Netherlands,
  so it is not the same posting.
- **Effective yield ≈ 5 / 50 (10%)**: 1 true same posting, 1 same-role
  same-company posting in another country, 3 comparable.
- **Concentration:** every replacement came from two companies, so a full
  run would fill the dataset with Stripe and Nebius postings.
- **Language shift:** 19 of the 50 targets were not in English; every
  replacement is English, so the cross-language subgroup would shrink.
- **Non-job removal:** target #40 is a paid placement programme (a
  non-job, like cal-06). Replacing it hides a data-quality issue instead
  of flagging it.

**Conclusion:** at about 10% effective yield the plan would replace
roughly 25 to 30 of 275 listings, from very few companies. The approach
needs changing before a full run.

**Next:** reviewer decision (see options in the pilot report).

## E006 — Full-text subset from Jobicy and Arbeitnow (2026-11-21)

**Question:** can a separate set of full-text listings be built within a
one-day time box, so results are not only measured on 500-character
snippets?

**API terms checked on 2026-11-21:**
- **Jobicy** (jobicy.com/jobs-rss-feed, "Fair use"): use in research tools
  and AI products allowed without individual permission; storing and
  processing allowed with no fixed retention; AI-derived outputs such as
  matching scores explicitly allowed; must credit Jobicy as the source;
  at most 1 request per second per IP, honour Retry-After on HTTP 429.
- **Arbeitnow** (arbeitnow.com/en/terms, section 11 "API"): API provided
  as is; users agree to link back to Arbeitnow.com; permission can be
  revoked at any time. The API response adds: "free public API for jobs,
  please do not abuse". Responses carry `x-ratelimit-limit: 50`, no
  documented window. A UK feed exists at arbeitnow.co.uk.
- **Rejected: Bundesagentur für Arbeit Jobsuche.** Its terms of use forbid
  using programming interfaces "to read out content from the portal or
  apps for the purpose of data collection and evaluation", and it has no
  official API. No requests were made.
- **Not used: Himalayas** (global remote jobs, 20 per request; little EU
  coverage for our CVs).

**Setup:** `collect-fulltext.ts`, 20 requests: Arbeitnow DE pages 1-3 and
UK pages 1-2 (5 s apart); Jobicy geo germany, europe, uk (100 each) and
12 role tags in Europe (50 each), 2 s apart. Attribution added to
`eval/README.md`. Pairs from `build-fulltext-pairs.ts`, seed 20261121.

**Result, pool:**
- All 20 requests succeeded (Arbeitnow page 3, truncated during the API
  check, worked this time). 1,867 listings collected, 700 duplicates
  removed, 1 already in the production pool, **1,166 in the pool**
  (Arbeitnow 899, Jobicy 267).
- 1,163 full, 3 thin; median 4,753 characters.
- Languages: English 788, German 241, Dutch 71, French 58, unknown 8.
- `non_job_suspect`: **17**. The first screening pass flagged 35, mostly
  false positives from benefits ("tuition reimbursement", "training
  programme") and "Program Manager" titles; patterns were tightened and
  the frozen pool re-screened without new requests. The 17 are graduate
  programme intakes, freelance "Ads Quality Rater" gig work, an "Academy"
  role and one engineering role whose text mentions self-employment.

**Result, subset:**
- **10 CVs and 100 pairs, not the approved 12 and 120.** Under the stricter
  own-role rule, 6 of the 12 approved CVs had fewer than 5 own-role
  candidates: cv-24 QA, cv-25 product manager, cv-26 UX designer, and all
  three Turkish CVs (cv-02, cv-16, cv-28). Their queries were written for
  Adzuna and are specific ("ux ui designer", "senior technical product
  manager"). Of the fallbacks, only cv-21 (Turkish data engineer), cv-20,
  cv-30 and cv-06 had enough; no other CV did.
- Final CVs: cv-01, cv-09, cv-11, cv-17, cv-18, cv-21, cv-20, cv-30,
  cv-27, cv-06.
- Pairs: own 50, neighbour 30, random 20; 92 unique listings; Arbeitnow
  66, Jobicy 34; all 100 full; `non_job_suspect` 1.
- Language: same 71, cross 28, unknown 1. Cross pairs are 10 from the one
  Turkish CV and 18 from English CVs against German, Dutch or French
  listings.
- **Quirks:** the stricter rule ignores seniority words, so cv-11
  (intern) gets mostly senior "Software Engineer" listings as own-role
  pairs (4 of 5). It matches words, not phrases, so "Senior Site
  Reliability Engineer (Data Platform)" counts as own-role for "data
  engineer".

**Conclusion:** a usable full-text set exists, inside the time box, but
it is smaller than planned and has only one Turkish CV. The Turkish
cross-language result will rest on the production set.

**Parked for later (not part of this task):** Jobicy could replace
Remotive in the app's own remote search. Remotive's API returns only 15
listings (E002), while Jobicy returned 100 per request with full
descriptions and terms that allow this use.

**Next:** reviewer decision on the shortfall, then label drafting.

## E007 — Full-text subset accepted; drafting setup (2026-11-21)

**Decision:** the full-text subset is accepted as built in E006: **10 CVs
and 100 pairs**. No rule change.

**Limitations of the full-text subset (reported with every result):**
- **Smaller than planned.** It fell short of the approved 12 CVs and 120
  pairs because the stricter own-role rule (every role word of
  `search_query` in the title) left 6 of the 12 approved CVs with fewer
  than 5 own-role candidates: cv-24 QA, cv-25 product manager, cv-26 UX
  designer, and the Turkish cv-02, cv-16 and cv-28. Their queries were
  written for Adzuna and are specific. Only 4 fallback CVs qualified, so
  the subset has 10 CVs and **only one Turkish CV** (cv-21).
- **Seniority words are ignored by the own-role rule.** cv-11 (intern)
  therefore has mostly senior "Software Engineer" listings as own-role
  pairs (4 of 5). Its own-role bucket is not an intern-level bucket.
- **Words, not phrases.** The rule checks that each role word appears in
  the title, not that they appear together. "Senior Site Reliability
  Engineer (Data Platform)" counts as own-role for "data engineer".

**Drafting setup:**
- No non-Gemini LLM API key is configured in this environment, so the
  drafts for all 550 pairs are written by **Claude Opus 5.5
  (`claude-opus-5-5`)** inside a Claude Code session, not by a repeatable
  API script. The prompt is `eval/LABELLING_GUIDE.md` as committed with
  this entry. Gemini, a system under evaluation, is not used for drafting.
- The drafter reads blind sheets: CV text and listing text only, no
  bucket, language tags, screening columns or persona metadata.
- **Limitation:** the same model wrote the 30 synthetic CVs and designed
  the persona twists. Hiding metadata cannot remove that knowledge, so
  drafts may share the CV author's assumptions. Human review of every
  pair and the reported change rate are the safeguard.
- Each draft has `draft_label`, `confidence`, `flag` and a one-line
  rationale in `notes` citing the deciding evidence.

## E008 — Drafts for all 550 pairs; review tool (2026-11-21)

**Setup:** drafts written by Claude Opus 5.5 (`claude-opus-5-5`) in a
Claude Code session, following `eval/LABELLING_GUIDE.md` as of commit
5d2942a (E007). Blind batches showed only the CV text and the listing text
(production set: up to 700 characters, which covers every snippet;
full-text set: up to 3,800 characters per listing). Drafts are in
`data/labels/labels.csv` and `data/labels/labels-fulltext.csv`;
`label`, `reviewed_change` and `labelled_at` are blank for every pair.

**Result:**

| Set | 0 | 1 | 2 | 3 | non_job | low confidence |
|---|---|---|---|---|---|---|
| Production (450) | 104 | 165 | 87 | 94 | 21 | 210 |
| Full-text (100) | 47 | 27 | 13 | 13 | 1 | 27 |

- Draft labels follow the selection buckets as expected: own-role pairs
  lean 2-3, neighbour pairs 1, random pairs 0.
- The one full-text listing flagged by the `non_job_suspect` screen
  (f-080, a graduate intake with a past start date) was also drafted
  `non_job`. Production-set non-jobs are mostly talent-marketplace
  pitches, a self-funded placement programme, a training course, a closed
  posting and a potential-opening (talent pool) ad.

**Drafting conventions to confirm in review** (the guide does not state
them explicitly):
- A listing whose visible text states no requirements, with a matching
  title and no contrary evidence, gets **3 with low confidence**, as the
  reviewer did on cal-01 and cal-07.
- **Seniority steps count in both directions**: a lead or senior CV
  against a mid-level role two steps below gets 1, like a junior CV
  against a senior role.
- **Specialty families**: a different family with none of the role's core
  skills is 0 (data scientist for a full-stack role); an adjacent family
  is 1 (data engineer for a Python backend role).
- **Hands-on duties older than 3 years** (an engineering manager who last
  coded in 2022) count as adjacent only, per the past-duties rule.
- **Required spoken languages** stated in the listing are hard blockers
  (0), including Dutch, German, French and Arabic requirements.

If review changes any of these, record it here and update the guide.

**Review tool:** `npm run review` starts `eval/scripts/review-server.ts`
on http://127.0.0.1:4610. It shows one pending pair at a time without
metadata, saves every decision immediately, resumes at the first pending
pair, and stops after 60 reviews per session. Tested end to end (accept,
change with note, undo, stale page, session limit, resume) against copies
of the label files, which were restored byte-for-byte afterwards.

## E009 — Method change: LLM-only reference labels (2026-11-21)

**Decision (reviewer):** the evaluation switches to **LLM-generated labels (Claude Opus 5.5), no human review**.
This supersedes the human-review workflow adopted in E003 and refined in
E004 and E008. Nothing in those entries is changed; they record the
history.

**What changed:**
- For all 550 evaluation pairs (450 production, 100 full-text), `label`
  was set equal to `draft_label`. Verified before the update: 550 unique
  pair IDs, 550 unique CV-listing combinations, every `draft_label` in
  0-3, no review fields set. Verified after: every row has
  `label == draft_label`, `reviewed_change` blank, all other columns
  unchanged. `labelled_at` stays blank because no review happened.
- The human-review step is removed from the active plan (README,
  labelling guide). The review tool (`npm run review`) stays in the
  repository for a possible future audit.
- The drafting conventions listed in E008 were never confirmed by a
  human; they are now part of the reference judge's behaviour.

**What is kept:** the calibration round (E003, E004) was labelled by the
reviewer and shaped the guide: the past-duties rule, the
required-core-framework rule with ecosystems, and the listing-quality
definitions. Its 10 pairs stay human-labelled and outside the evaluation.

**Limitations (reported with every result):**
- Metrics measure agreement with an LLM reference judge, not with human
  recruiters.
- The same model (Claude Opus 5.5) generated the 30 synthetic CVs and the
  reference labels.
- Agreement between the reference labels and human judgements was never
  measured.

## E010 — Baseline run: heuristic and Gemini (2026-11-21)

**Reference:** LLM-generated labels (Claude Opus 5.5), no human review
(E009). Every number below is agreement with that LLM reference judge, not
with human recruiters; agreement with humans was never measured.

**Setup (identical for both systems):**
- Pairs: the frozen 450 production pairs (`pairs.csv`) and 100 full-text
  pairs (`pairs-fulltext.csv`), with their snapshots and reference labels
  as committed in 1ec749a.
- Inclusion: pairs flagged non_job are excluded and counted (21
  production, 1 full-text; 528 genuine). A pair whose prediction did not
  return a score is excluded for that system and counted as a failure.
  Production and full-text are reported separately, with thin/full and
  same/cross-language subgroups.
- Metrics (`eval/scripts/metrics.py`): precision/recall/F1 with match =
  label ≥ 2 and predicted match = score ≥ 50 (fixed in advance, not tuned);
  Spearman ρ; NDCG@5 and NDCG@10 per CV; 95% CV-level bootstrap, 1,000
  resamples, seed 20261121.
- Heuristic (`run-heuristic.ts`): the app's `scoreListing`, given the CV's
  extracted skills and the persona's target-role search query, country and
  seniority. Caveat: that query was also used to fetch the persona's own-role
  listings, which may favour the heuristic; Gemini gets no query, and the
  reference labeller saw no metadata.
- Gemini (`run-gemini.ts`): the app's `analyze()` with gemini-2.5-flash,
  output language en, using its `fit_score`. Responses cached locally
  (gitignored).

**Coverage:**

| System | Set | Genuine | Scored | Failed / not run |
|---|---|---|---|---|
| Heuristic | Production | 429 | 429 | 0 |
| Heuristic | Full-text | 99 | 99 | 0 |
| Gemini | Production | 429 | 22 | 4 quota errors, 403 not run |
| Gemini | Full-text | 99 | 0 | 99 not run |

**Blocker:** the Gemini run hit the free-tier daily request quota
(`GenerateRequestsPerDayPerProjectPerModel-FreeTier`) after 23 successful
calls, at 4 parallel requests. A sequential retry later the same day hit the
same quota id immediately. The remaining 527 pairs need roughly 23 more days of
free-tier quota at about 23 calls per day, or a paid tier. The runner resumes from
the cache.

**Results (production, all genuine):**

| System | n | Precision | Recall | F1 | Spearman ρ | NDCG@5 | NDCG@10 |
|---|---|---|---|---|---|---|---|
| Heuristic | 429 | 0.68 [0.57, 0.78] | 0.87 [0.81, 0.93] | 0.76 [0.69, 0.83] | 0.65 [0.54, 0.75] | 0.80 [0.70, 0.88] | 0.87 [0.81, 0.92] |
| Gemini (partial) | 22 | 0.71 [0.45, 0.92] | 1.00 | 0.83 [0.62, 0.96] | 0.86 [0.62, 0.96] | 1.00* | 1.00* |

\* Trivial: the 22 pairs cover 16 CVs with at most two pairs each.

Full-text, heuristic (n = 99): precision 0.60 [0.37, 0.82], recall 0.81
[0.69, 0.93], F1 0.69 [0.49, 0.84], Spearman 0.65 [0.51, 0.75], NDCG@5
0.72 [0.62, 0.82], NDCG@10 0.83 [0.75, 0.90].

Head-to-head on the 22 production pairs both systems scored: F1 0.83 vs
0.83, Spearman 0.71 vs 0.86 (heuristic vs Gemini). Too small to conclude
anything.

**Thin listings:** 418 of 429 genuine production pairs are thin, and the
heuristic's thin-subgroup numbers (F1 0.77, Spearman 0.66) match the whole
production set. The 11 full production listings contain no label ≥ 2 pair.

**Conclusion so far:** the heuristic baseline is complete. No comparison
with Gemini is drawn until its run covers the same pairs. Full tables:
`eval/results/2026-11-21-baselines.md`.

## E011 — Method change: Gemini on a 100-pair sample (2026-11-21)

**Decision (reviewer):** no paid Gemini tier. Gemini is evaluated on a fixed
100-pair sample instead of all 528 genuine pairs; the heuristic is still
reported on all 528. The comparison between the systems is heuristic vs
Gemini on the same 100 pairs. This supersedes the Gemini part of E010;
E010's Gemini numbers (22 pairs, the first pairs by ID) are kept as history
and not used.

**Sample** (`eval/scripts/draw-sample.py` → `eval/data/gemini-sample.csv`):
- Population: the 528 genuine pairs (non_job excluded), both sets.
- Stratified by set × bucket, proportional allocation with largest-remainder
  rounding, simple random sampling within strata, seed 20261121:

  | Set | own | neighbour | random | Total |
  |---|---|---|---|---|
  | Production | 43 of 225 | 27 of 145 | 11 of 59 | 81 |
  | Full-text | 9 of 50 | 6 of 30 | 4 of 19 | 19 |

- Drawn independently of Gemini: the script reads only pairs and label
  flags, never predictions or cached responses. Cached responses were
  reused only for sample pairs that already had one (5 of 100: p-001,
  p-003, p-010, p-014, p-051).

**Collection:** `eval/scripts/gemini-daily.sh` runs `run-gemini.ts` on the
sample once a day at 12:00 local time (after the midnight-Pacific quota
reset) as a launchd agent, `com.applypilot.eval-gemini-sample`, with one
request at a time. A 429 naming the daily quota stops the run at once;
cached pairs are never re-requested. When all 100 pairs are ok or refused,
the job regenerates the report with `metrics.py` and uninstalls itself.
Nothing is committed automatically. First manual run: 7/100 complete (2
new responses before the quota error). At about 20 requests a day the
sample should complete in about 5 days.

**Metrics changes:**
- `metrics.py` now reports (1) the heuristic on all genuine pairs, per set,
  with thin/full, language and own/neighbour/random subgroups, and (2)
  heuristic vs Gemini on the sample pairs both systems scored, overall, per
  bucket and per set. Interim reports are marked incomplete.
- Each evaluation uses its own generator seeded with 20261121, so a group's
  bootstrap interval no longer depends on which groups were computed before
  it. Point estimates are unchanged. Some E010 intervals moved by up to
  0.02 (for example full-text precision [0.37, 0.82] → [0.38, 0.83]).
- The report file is named after the run date.

**Limitations of the sample** (also in eval/README.md):
- Intervals are much wider than on 528 pairs. The random bucket has 15
  pairs with few or no label ≥ 2 pairs, so per-bucket results are only
  indicative.
- About three pairs per CV: NDCG is weak evidence (a CV with one pair
  always scores 1.00). Compare on F1 and Spearman.
- The heuristic's sample numbers differ from its all-pairs numbers by
  sampling noise. Only the sample rows compare the systems.
- Production (81, mostly thin) and full-text (19) are pooled in the
  sample. Per-set results inside it are small.
- Responses are collected over several days under one model name, so a
  silent model update by Google in that period would not be visible.
- All numbers remain agreement with the LLM reference judge, not with
  humans.
